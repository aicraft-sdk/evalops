Documentation & Showcase

EvalOps — "SonarQube for AI"

A production-ready platform for evaluating, monitoring, and enforcing quality gates on LLM-based features. Run structured evaluations against prompts, datasets, and agents, enforce pass/fail policies, track cost and drift, and ship LLM changes with CI/CD-grade confidence.

System design

Four services, one gateway

EvalOps is an Nx monorepo built as four NestJS microservices plus a React frontend and a Python worker, all communicating through a single API Gateway. There is no integration-service or analytics-service anymore — both were fully decommissioned and their real functionality now lives inside core-service, mounted as libs/core-integration and libs/core-analytics.

Workflow

An eval run, from trigger to policy gate

The same flow runs whether it's kicked off by a developer via the CLI, a script using the SDK, or the GitHub Action on a pull request.

Policy engine. Policies define pass/warn/fail thresholds (e.g. minimum pass rate, cost budget). A failing policy returns a non-zero exit code from the CLI and the evaluate-pr action, so a bad LLM change blocks the merge the same way a failing unit test would.
Capabilities

What's actually implemented

Every item below maps to real code in this repository — nothing here is aspirational.

Security & Isolation

Multi-tenant isolation PostgreSQL Row Level Security keyed on app.org_id, set per-request by OrgContextInterceptor.
JWT auth at the gateway JwtAuthGuard + RbacGuard run as a global APP_GUARD on every service. Microsoft Entra ID SSO is implemented and env-gated; other SSO providers aren't yet supported.
Audit trail & structured logging Every mutation logged with user/org/timestamp; every request emits pino-backed JSON with request/trace correlation.

Evaluation Engine

Policy engine + CI/CD gates Pass/warn/fail thresholds evaluated per run; non-zero exit codes block CI merges.
Multi-provider evaluation engine Exact match, rule-based, LLM-as-judge, RAG metrics, and safety evaluators across OpenAI, Azure OpenAI, Anthropic, Gemini, and xAI.
Sandboxed code execution Runs via core-service's sandbox API — an HTTP client (SandboxService) against an external OpenSandbox server, bring your own backend, not a bundled Docker runner.

Observability & Cost

OpenTelemetry HTTP/Postgres/Redis auto-instrumented, OTLP gRPC export to any OTel collector.
Cost analytics Per-run, per-provider, and per-model token cost tracking, captured on every evaluation run.
Trace event ingestion Agents stream events in-flight to runs.trace_events (10 MB cap, rate-limited).

Developer Tools & Integrations

CLI @evalops/cli — login, eval run, dataset push, agent publish, policy check, doctor.
JS & Python SDKs EvalOpsClient ships in TypeScript and Python, including an optional pytest plugin for gating tests on an eval spec.
Webhook & CI/CD integrations Outbound webhook delivery on run completion, plus a composite GitHub Action for PR gating.
How to use

Getting started

Local setup requires Node.js 20+, PostgreSQL, and (optionally, for webhooks/rate limiting) Redis.

1. Install and configure

npm install
cp .env.example .env
# Edit .env — set JWT_SECRET, SERVICE_SECRET, and at least one AI provider key
#   (OPENAI_API_KEY or AZURE_OPENAI_API_KEY)

2. Provision Postgres + Redis (Docker)

docker run -d --name evalops-postgres -p 5432:5432 \
  -e POSTGRES_DB=evalops -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=postgres \
  postgres:15-alpine

docker run -d --name evalops-redis -p 6379:6379 redis:7-alpine

3. Run migrations and start everything

npm run db:push

tilt up          # Recommended: Tilt dev dashboard at http://localhost:10350
# OR
npm run dev       # All services in parallel, no Tilt
Access pointURL
Frontendhttp://localhost:4200
API Gatewayhttp://localhost:3000
Swagger docshttp://localhost:3000/api/docs (and each service on its own port)

4. Authenticate against the API

All routes go through the gateway on a single /api prefix. Every endpoint except login/register/logout/health requires a Bearer JWT. 

# Register
curl -X POST http://localhost:3000/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","password":"Password123!"}'

# Login → get a JWT
curl -X POST http://localhost:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","password":"Password123!"}'

# Use the token
curl http://localhost:3000/api/core/prompts \
  -H "Authorization: Bearer <token>"
First real workflow. Once services are up: register/login, create a dataset, create a prompt, create an eval spec linking the two plus an evaluator list, then run the evaluation and watch the verdict in the UI or via evalops eval run --watch.
Command line

@evalops/cli

Wraps the REST API so you don't have to hand-craft curl commands, either from a terminal or from a CI pipeline. Works from inside the monorepo (npm run evalops --) or as the standalone @evalops/cli package once installed. 

# From inside the monorepo
npm run evalops -- <command>

# Credentials, checked in this order:
#   1. EVALOPS_API_KEY (JWT token)
#   2. EVALOPS_SERVICE_TOKEN (service-to-service token)
#   3. ~/.evalops/credentials.json (saved by `evalops login`)
# API URL defaults to http://localhost:3000, override with EVALOPS_API_URL

login

Authenticate and save the JWT to ~/.evalops/credentials.json.

npm run evalops -- login --url=https://evalops.internal

eval run <spec-name> [--watch]

Trigger a run for a named eval spec, optionally poll until it completes.

npm run evalops -- eval run "Production Quality Gates" --watch
# Waiting for completion...........
# ✅ PASS — pass rate: 94.3% — cost: $0.0124

Exit code 0 = pass, 1 = failed policy check.

dataset push <file.json>

Upload a dataset from a local JSON file ({ name, description, samples[] }).

npm run evalops -- dataset push ./datasets/fraud-golden-set.json

agent publish <agent.md>

Publish an AgentMD file as a new versioned entry in the agents registry.

npm run evalops -- agent publish ./agents/fraud-detection.md

policy check <run-id>

Print the policy verdict for a completed run. Exits 1 on fail — useful for scripting.

npm run evalops -- policy check $RUN_ID || echo "Quality gate failed!"

doctor

Checks Node version, Docker, auth, gateway/service health, and required env vars.

npm run evalops -- doctor
#   ✅  Node.js v20.19.0
#   ✅  Auth  (EVALOPS_API_KEY set via env)
#   ✅  API Gateway  (http://localhost:3000)
#   ✅  auth-service  (:3001)
#   ✅  core-service  (:3002)
#   ✅  evaluation-service  (:3003)
Client libraries

JS & Python SDKs

Both SDKs wrap the same REST API as the CLI, so a script can push datasets, create runs, and wait for a verdict without shelling out.

JavaScript / TypeScript — libs/sdk

EvalOpsClient exposes datasets, specs, runs, agents, policies, tokens, and ingest resources.

import { EvalOpsClient } from '@evalops/sdk';

const client = new EvalOpsClient({
  baseUrl: 'http://localhost:3000',
  token: process.env.EVALOPS_TOKEN!,
});

const spec = await client.specs.upsertFromYaml('./evals/my.eval.yaml');
const run  = await client.runs.create({ evalSpecId: spec.id });
const done = await client.runs.waitFor(run.id, { timeoutMs: 60_000 });

if (done.decision === 'fail') process.exit(1);

Python — evalops-sdk

Ships with an optional pytest plugin for gating tests directly on an eval spec.

pip install evalops-sdk
# With pytest plugin:
pip install "evalops-sdk[pytest-evalops]"
from evalops import EvalOpsClient

client = EvalOpsClient(base_url="http://localhost:3000", token="evops_pat_...")
spec = client.specs.upsert_from_file("my-eval.yaml")
run = client.runs.create(spec.id)
done = client.runs.wait_for(run.id, timeout_ms=120_000)
print(done.decision)  # pass | warn | fail
# pytest plugin — set EVALOPS_URL and EVALOPS_TOKEN
@pytest.mark.evalops("my-eval.yaml")
def test_pipeline():
    pass
CI/CD

GitHub Action

The bundled evaluate-pr composite action runs a suite, posts the verdict as a PR comment, and uploads JUnit results as a workflow artifact. 

- uses: ./.github/actions/evaluate-pr
  with:
    suite-name: "Production Quality Gates"
    org-id: ${{ secrets.EVALOPS_ORG_ID }}
    api-key: ${{ secrets.EVALOPS_API_KEY }}
    api-url: ${{ secrets.EVALOPS_API_URL }}
    fail-on-warn: "true"

Prefer plain CLI invocation instead? That works from any CI provider: 

- name: Run eval gate
  run: npm run evalops -- eval run "Production Quality Gates" --watch
  env:
    EVALOPS_API_KEY: ${{ secrets.EVALOPS_API_KEY }}
    EVALOPS_API_URL: ${{ secrets.EVALOPS_API_URL }}
Security model

Auth, isolation, and observability

Authentication JWT

Every service registers JwtAuthGuard as a global APP_GUARD. Routes that must stay public (login, register, health checks, the GitHub webhook path) opt out with @Public(). The gateway enforces this itself now (not just downstream), and also rejects path-traversal sequences in proxied paths before forwarding.

Microsoft Entra ID (Azure AD) SSO is implemented via MSAL (apps/auth-service/src/app/auth/microsoft/), reachable through the gateway's /api/auth/* proxy as GET /api/auth/microsoft (login redirect) and GET /api/auth/microsoft/callback (issues a real JWT, sets an httpOnly cookie). It's env-config-gated — disabled unless MICROSOFT_CLIENT_ID, MICROSOFT_CLIENT_SECRET, and MICROSOFT_TENANT_ID are set. SSO currently supports Microsoft Entra ID only; other providers are not yet implemented.

Authorization RBAC

RbacGuard + @Roles() enforce role checks. Role hierarchy: admin > org_admin > member > viewer.

Multi-tenant isolation RLS

OrgContextInterceptor sets the Postgres session variable app.org_id on every request; Row Level Security policies enforce org-scoped access at the database layer, e.g.: 

CREATE POLICY tenant_isolation ON prompts
  USING (organization_id = current_setting('app.org_id', true)::uuid);

Service-to-service auth

Internal routes (like the artifact-notify endpoint) are protected by ServiceAuthGuard, checking an X-Service-Token header against SERVICE_SECRET.

Rate limiting

The trace ingestion endpoint is limited to 100 requests/user/minute via a Redis-backed sliding window; it degrades gracefully if Redis is unavailable.

Audit trail & structured logging

Every mutation is logged with user, org, and timestamp. Every request emits pino-backed JSON with request/trace correlation, including requests rejected by a guard.
